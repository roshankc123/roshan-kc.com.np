Direct answer: elephc and TypePHP are compilers: they turn typed PHP into machine code to make CPU-heavy code faster. NativePHP is an app framework: it bundles the normal PHP runtime inside iOS, Android and desktop apps so Laravel developers can ship client apps. If you want an app, use NativePHP. If you want speed, look at elephc or TypePHP, and for most web apps, try Octane or FrankenPHP first.

"Native PHP" now means two unrelated things, and they get mixed up constantly. That's understandable: all three projects took off in 2026 and all three put "PHP" and "native" in the same sentence. This is the hub for a short series. It explains the split, compares the three in one table, and links to deeper posts on each.

The two meanings of "native PHP"

Meaning 1: PHP compiled to native code. Your PHP source becomes a machine-code binary, a shared library or a PHP extension, with no interpreter loop at runtime. That's elephc and TypePHP. The goal is performance and portability.

Meaning 2: PHP running inside a native app. Your PHP stays PHP, interpreted by a real PHP engine, but that engine lives inside an iOS, Android or desktop app with native UI and device APIs. That's NativePHP. The goal is reach: one Laravel codebase on phones and desktops.

Once you see that split, the "which is better" question mostly goes away. They don't compete.

Which one do you need?

  1. "Our clients want a mobile app and we're a Laravel shop." NativePHP. Read NativePHP in 2026 for the trade-offs against Flutter and React Native.
  2. "Our web app is slow." None of them, at first. Profile. Most slow Laravel apps are slow because of queries and per-request boot. Octane with Swoole or FrankenPHP is the proven fix.
  3. "One function is CPU-bound and we've already optimised it." That's when an AOT compiler earns a look. Compile that module as an extension with elephc or TypePHP. See elephc vs TypePHP.
  4. "I want to ship a CLI tool as one binary." elephc.
  5. "We run Swoole or Hypervel in production." Watch TypePHP; it's built by the same team for that world.

Can you use them together?

In principle, yes, and this is the most interesting idea in the whole space. elephc can cross-compile PHP into iOS ARM64 static libraries. NativePHP apps are Swift and Kotlin shells around PHP. A compiled PHP library called from a NativePHP plugin would give you native-speed PHP for one hot routine and Laravel for everything else, on a phone.

I haven't found a published, working example of that combination. Treat it as a possibility, not a recipe. The simpler pairing works today: elephc or TypePHP compile a PHP extension for your server, and NativePHP ships the client.

Common misconceptions

  • "NativePHP compiles PHP." It doesn't. Your PHP is interpreted on the device. Only the UI is native.
  • "TypePHP or elephc will make my Laravel app 8× faster." Not today. Both compile a typed subset, and framework code is full of dynamic behaviour they can't compile. Published speedups come from CPU-bound benchmark scripts.
  • "AOT replaces the JIT." They solve related problems in different places. The JIT (PHP 8.0+) optimises hot code inside the running engine; AOT compiles before the program runs. You can run a compiled extension inside a JIT-enabled PHP.
  • "This is HHVM again." Partly. HHVM showed PHP could be compiled and also that ecosystem compatibility decides adoption. I go into that in the future of native PHP.

Key takeaways

  • "Native PHP" means two things: compiling PHP to machine code (elephc, TypePHP) and embedding PHP in native apps (NativePHP).
  • NativePHP is the stable, production choice for Laravel developers building iOS, Android and desktop apps.
  • elephc and TypePHP are experimental AOT compilers for typed, CPU-bound code. Use them for isolated modules, not whole frameworks.
  • For a slow web app, start with profiling and Octane or FrankenPHP, not a compiler.
  • The tools can coexist: compile a hot server module, ship the client with NativePHP.
