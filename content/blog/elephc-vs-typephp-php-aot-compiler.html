Direct answer: elephc and TypePHP both compile PHP ahead of time to native code, but they take opposite routes. elephc (Rust, MIT) emits assembly directly and drops the Zend Engine entirely. TypePHP (Swoole, GPL-3.0) translates PHP to C++ and keeps a bridge to the Zend runtime. Pick elephc for small standalone binaries and PHP extensions; pick TypePHP if you live in the Swoole world and want closer compatibility with existing PHP. Neither is production-ready for a full framework app as of November 2026.

Two serious PHP AOT compilers showed up within months of each other in 2026, after years of "PHP can't be compiled" being accepted wisdom (HHVM's story aside). If you're choosing which one to experiment with, the useful question isn't "which is faster". It's "which design fits the code I actually have". I've already written up what elephc is and what TypePHP means for PHP performance; this post puts them side by side.

What does an AOT compiler for PHP do?

An ahead-of-time (AOT) compiler turns PHP source into machine code before the program runs. Normal PHP compiles your script to opcodes at runtime and runs them in the Zend Engine's virtual machine; OPcache caches the opcodes, and the JIT (since PHP 8.0) compiles some hot ones to machine code while the program runs. AOT moves all of that to build time, which only works when the compiler can figure out your types in advance. That's why both projects target a subset of PHP.

The design difference that matters

elephc removes the runtime; TypePHP replaces the interpreter but keeps the runtime. Almost every practical difference follows from that.

Because elephc has no Zend Engine, its binaries are self-contained and it can target places PHP doesn't normally go, like an iOS static library. The cost: every PHP function you call has to be reimplemented by the elephc team. That's why it publishes coverage numbers (74% of a default PHP 8.5 build's functions as of v0.27.8) and why unsupported behaviour is a compile error.

TypePHP's approach, as Albert Chen put it in a May 2026 talk on Swoole's AOT compiler, "throws out the opcode handler — not the runtime — and links straight against libphp.so." PHPX, a header-only C++ library mirroring PHP's standard library, sits between your compiled code and Zend. You inherit PHP's real behaviour for the dynamic parts, and your build depends on a matching PHP installation.

How strict do you have to be?

Both want typed, predictable code, but they enforce it differently.

TypePHP's documented restrictions include: the global scope is declaration-only (code goes in functions, with a strict main() for binaries); inferred int, float and bool values use fixed native storage and can't later change type; PHP-compatible integer overflow needs use varint_types; and some highly dynamic reference, closure and reflection patterns aren't supported. The May 2026 talk also listed no $$name or extract(), no yield generators, and strict function arity.

elephc infers types and supports more of the language surface than you'd guess, including generators, Fibers, traits and references. Its limit shows up in the standard library and in dynamic behaviour it can't resolve at compile time.

If your code already passes PHPStan at a high level with real types everywhere (see how PHP's type system got here), you're in good shape for either.

What about speed?

The only numbers available are the projects' own, so treat them as directional. TypePHP's README reports bench.php dropping from 5.034 s interpreted to 0.603 s compiled at -O3 (about 8×), and micro_bench.php from 13.045 s to 2.021 s (about 6.5×). In his talk, Albert Chen showed a recursive fib(40) going from about 14.8 s to 0.11 s. elephc publishes no headline benchmark; its showcase is DOOM running at the game's native 35 tics per second.

Two cautions. These are CPU-bound micro-benchmarks, and a typical web request spends most of its time waiting on a database. And I haven't seen an independent, like-for-like benchmark of the two compilers. If you run one, publish your scripts.

Which should you choose?

A short decision list:

  1. Writing a PHP extension instead of C? Either works. elephc has the lighter toolchain; TypePHP is closer to real PHP semantics.
  2. Need a self-contained binary with no PHP install on the target? elephc.
  3. Targeting iOS? elephc's iOS static libraries are the clearer path today.
  4. Already running Swoole, Hypervel or Workerman? TypePHP. The Swoole team built it for that world, and the talk reports Workerman compiling to a single binary "with only minor patches".
  5. Shipping closed-source commercial software? Read the licences. GPL-3.0 (TypePHP) and MIT (elephc) have very different obligations if you distribute the compiler or linked runtime.
  6. Want to compile your whole Laravel app? Neither, yet. Use Octane or FrankenPHP and compile only a hot module.

My own lean, for what it's worth: I'd use elephc to learn and to build tools, and watch TypePHP for server workloads, because keeping the Zend runtime is the more realistic route to compiling real-world code eventually.

Key takeaways

  • Both are PHP ahead-of-time compilers for a typed subset; neither compiles a full Laravel or Symfony app today.
  • elephc (Rust, MIT) emits assembly with no Zend Engine: self-contained binaries, PHP extensions and iOS libraries.
  • TypePHP (Swoole, GPL-3.0, written in PHP) goes through C++ and links against libphp via PHPX, trading self-containment for compatibility.
  • Published speedups (6.5×–8× on the README's benchmark scripts) are the vendors' own CPU-bound numbers, not web-app results.
  • Choose on design fit and licence, and compile isolated hot paths rather than whole applications.
